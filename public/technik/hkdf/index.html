Zwei Schlüssel aus einem Geheimnis

Von Nasser Aldin Farag / 0xFarag

Offline-Beispiel herunterladen (.py)

Zwei Seiten können mit X25519 unabhängig denselben geheimen Wert berechnen. Woher wissen sie, welche 32 Bytes später für welche Aufgabe gelten? Das Protokoll muss diese Aufgabe benennen. HKDF kann aus dem gemeinsamen Geheimnis beispielsweise je einen Schlüssel für die Hin- und Rückrichtung ableiten. Beide Seiten müssen sich über Rolle, Reihenfolge und Kontext einig sein. RFC 7748, Abschnitt 6.1

Bei AuthzLedger 1.5.0 prüft der Empfänger mit Ed25519 das signierte Inventar eines Übergabepakets. Der öffentliche Prüfschlüssel muss dem erwarteten Absender unabhängig zugeordnet werden. Dieses Blatt erläutert eine andere kryptografische Aufgabe, die Ableitung symmetrischer Schlüssel. Das beiliegende X25519/HKDF-Beispiel läuft eigenständig und beschreibt keine freigegebene Transportfunktion von AuthzLedger. AuthzLedger 1.5.0

Was Extract und Expand leisten

Für SHA-256 berechnet Extract den 32 Byte langen Zwischenschlüssel PRK = HMAC-SHA256(salt, IKM). Der Salt ist der HMAC-Schlüssel, das ursprüngliche Schlüsselmaterial die Nachricht. Für einen fehlenden Salt legt RFC 5869 einen Standardwert aus 32 Nullbytes fest. Ein verfügbarer, unabhängiger Zufallssalt kann öffentlich sein. Beide Seiten müssen denselben Wert verwenden. Extract nutzt die vorhandene Entropie. Ein leicht erratbares Geheimnis bleibt auch mit Salt leicht erratbar. Für Passwörter braucht es ein dafür ausgelegtes, rechen- und vorzugsweise speicherintensives Verfahren. RFC 5869, Abschnitte 2 und 3

Expand erzeugt aus PRK, Kontext info und gewünschter Länge L das Ausgabematerial. Bei SHA-256 sind je Expand-Aufruf höchstens 8’160 Byte möglich. Zweck, Protokollversion und Senderichtung erhalten eindeutige Kodierungen. Nur die Ausgabelänge zu verändern trennt keine Zwecke: Mit demselben PRK und Kontext entsprechen die ersten 16 Byte einer 32-Byte-Ausgabe exakt der 16-Byte-Ausgabe. RFC 5869, Abschnitt 2.3

Was das Beispiel überprüft

  1. Der öffentliche Testfall A.1 liefert erwartete Werte für PRK und die 42-Byte-Ausgabe. Das Programm prüft die getrennten Phasen und die kombinierte HKDF-Funktion gegen diese Werte. So kann eine vertauschte HMAC-Parameterreihenfolge oder ein falscher Kontext auffallen. Testvektor A.1
  2. Zwei lokal erzeugte, kurzlebige X25519-Schlüsselpaare berechnen das Geheimnis jeweils von ihrer Seite aus. Ein Kontext bindet beide öffentlichen Schlüssel in der festen Reihenfolge Client, Server. Jede Seite erhält dieselben zwei Richtungsschlüssel. Ein vertauschtes Rollenpaar liefert für denselben Richtungsnamen einen anderen Schlüssel. Das Programm gibt ausschliesslich Prüfergebnisse aus. Python-Bibliothek
  3. Die öffentlichen Schlüssel sind im Beispiel direkt im selben Prozess verfügbar. Bei einer Netzwerkverbindung braucht der Handshake zusätzlich einen Vertrauensnachweis für die Gegenstelle und eine vereinbarte Behandlung ungültiger Peer-Eingaben. Die Einbeziehung öffentlicher Schlüssel in info allein bestätigt keine Identität. RFC 7748, Abschnitte 6 und 7

Ein häufiger Fehler bei Nonces. Eine konstante HKDF-Ausgabe als Nonce für mehrere Nachrichten mit demselben ChaCha20-Poly1305-Schlüssel würde dessen Einmaligkeitsanforderung verletzen. RFC 8439 verlangt pro Verschlüsselung unter demselben Schlüssel eine eindeutige 96-Bit-Nonce. Zählerstände müssen gegebenenfalls Neustarts überstehen oder mit frischen Schlüsseln neu beginnen. AEAD liefert bereits den Authentifizierungstag für die Nachricht. Das Lernbeispiel endet vor der Verschlüsselung. RFC 8439, Abschnitt 2.8

Lokal ausführen

Voraussetzung ist eine Python-Umgebung mit cryptography ab Version 40. Mit Python 3.12 und cryptography 50.0.0 wurde das Programm erfolgreich ausgeführt.

python hkdf_demo.py
